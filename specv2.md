# Spreadsheet Utility – Specification v2

A simple spreadsheet application written in **Python 3.14t** (free-threaded, no GIL), with a PyQt6 UI and a parallel dependency-driven recalculation engine.

## 1. Goals and non-goals

**Goals**
- A correct, well-tested single-sheet spreadsheet with formulas, ranges, formatting, undo/redo and CSV import/export.
- A recalculation engine that uses a dependency DAG and recalculates independent branches in parallel.
- Test-first development, with CI.

**Non-goals (v1)**
- Multiple sheets, named ranges, charts, macros, `.xlsx` import/export.
- Cross-sheet references (`Sheet!A1`).

## 2. Architecture overview

Two layers with a strict dependency direction: **UI -> Engine**. The engine has no Qt imports and is fully testable headless. Because PyQt6 has no free-threaded wheel (section 16, entry 99), the two layers run in **separate processes with separate interpreters**: the engine on free-threaded 3.14t, the UI on standard 3.14, joined by a JSON-lines protocol over the engine's stdin/stdout (entries 105-115).

```
sheet/
  engine/     lexer, parser, ast, evaluator, cell store, graph, recalc, formats, dates, csv_io, history
  ui/         PyQt6 model, view, main window
  tests/
    engine/   no Qt needed
    ui/       run with QT_QPA_PLATFORM=offscreen
  benchmarks/
  scripts/    setup.sh, run.sh, test.sh
```

Implementation order (each step is complete, tested and working before the next):
1. Lexer, parser, AST, evaluator (single-threaded, correct).
2. Cell store, formats, dates.
3. Dependency graph with cycle detection and rollback.
4. Transactions, undo/redo, structural edits, copy/paste.
5. Parallel recalculation and benchmarks.
6. CSV I/O. **[Superseded by entry 137: `^` is now left-associative, as in Excel.]**
7. PyQt6 UI.

## 3. Project setup and tooling

- Managed with **uv**. Two environments are created from the one `pyproject.toml`: `.venv`, free-threaded Python **3.14t**, for the engine, its tests and the benchmarks; and `.venv-ui`, standard Python 3.14 with PyQt6, for the UI (PyQt6 has no free-threaded wheel; see section 16, entries 99-105).
- `scripts/setup.sh` installs both; `scripts/ui_python.sh` finds (or installs) the standard Python 3.14 for the UI; `scripts/run.sh` starts the application (the UI starts the engine process itself); `scripts/test.sh [engine|ui]` runs the tests and exits non-zero on any failure; `scripts/bench.sh` runs the parallel-recalculation benchmarks.
- Tools: `pytest`, `hypothesis` (property tests and fuzzing), a small custom benchmark harness, `ruff` (lint and format) and `mypy --strict`.
- **Supported platforms: macOS and Linux** (both tested: macOS locally, Ubuntu in CI). Windows is not supported or tested, and the scripts are bash.
- The early spike result: PyQt6 does not install on 3.14t, so the UI runs in its own interpreter and the engine in a separate free-threaded process.

## 4. Testing and CI

- **Test first:** for each feature, write failing tests, then implement until they pass.
- Test layers: unit (lexer/parser/evaluator/dates/formats), property-based (hypothesis), integration (engine end-to-end), UI (offscreen Qt), benchmarks.
- **GitHub Actions** runs on every push to `main` and every pull request (Ubuntu): both environments are installed from scratch, `ruff` and `mypy` run for engine and UI, then the engine tests (3.14t) and the UI tests (standard 3.14, offscreen Qt, against a real engine process) run as separate steps. Timing benchmarks run locally only.
- The README shows a CI status badge and a test-count badge: CI converts the JUnit reports into a shields.io endpoint file on a `badges` branch (no secrets needed; public repositories only).
- **Fuzzing is part of the suite**: random bytes through the server loop, random garbage and random valid command sequences through the request handler (checking that failed requests change nothing and the graph always matches the formulas).

## 5. Grid and cell store

- Addressable grid: **1,048,576 rows x 16,384 columns** (A1 to XFD1048576), as in Excel.
- Storage is a **sparse `dict[(row, col)] -> Cell`**. Only non-empty cells exist. Memory is proportional to the number of populated cells, and reads and writes are O(1).
- There is no CSR structure, no write buffer and no row chunking. The dict is the source of truth. UI responsiveness comes from the threading model in section 10, not from buffering.
- Cell addresses use 0-based `(row, col)` internally; A1 notation is parsed and rendered at the edges only.

### Cell

A `dataclass(slots=True)`:

| Field | Description |
|---|---|
| `text` | The raw text the user entered. |
| `ast` | Root node of the parsed expression, or `None` for non-formula cells. |
| `value` | `float \| str \| bool \| ErrorValue \| None` (None = empty). |
| `format` | Number format string, e.g. `"General"`, `"DD/MM/YYYY"`, `"$#,##0.00"`. Per-cell strings are interned so identical formats share one object. |
| `error` | Error kind and message, when `value` is an `ErrorValue`. |

Rules:
- Entering a number, boolean or text constant creates a cell with no AST; `value` is parsed directly. Entries starting with `=` are formulas.
- **Constant folding:** at parse time any sub-expression made only of literals is replaced with a `Literal` node holding the computed value. Entering `=1/2` stores `text="=1/2"` and an AST that is just `Literal(0.5)`, so evaluation never recomputes it.
- Errors: `#DIV/0!`, `#REF!`, `#NAME?`, `#VALUE!`, `#NUM!`. A formula that references an error cell propagates that error.

## 6. Formula language

- **Parsing:** hand-written lexer and **recursive-descent parser**. Lexing, parsing and AST construction happen **once, on data entry**. Recalculation walks the stored AST and never re-parses.
- **Operators (high to low precedence):** unary `-` `+`; `%` postfix; `^` (left-associative, as in Excel: `=2^3^2` is 64); `*` `/`; `+` `-`; `&` (string concat); comparisons `= <> < > <= >=`. Parentheses are supported.
- **Literals:** numbers (including `1.5e3`), strings in double quotes (`""` escapes a quote), `TRUE` / `FALSE`.
- **References:** `A1`, `$A$1`, `$A1`, `A$1` (case-insensitive); ranges `A1:A45`. Whole-column and whole-row ranges (`A:A`, `1:1`) are **not** supported (removed from the spec; use an explicit range such as `A1:A1048576`).
- **Functions (v1):** `SUM`, `AVERAGE`, `MAX`, `MIN`, `COUNT`. Others may be added through a function registry.
- **Semantics:**
  - Range functions ignore empty cells, text and booleans inside ranges; they error on error values.
  - `AVERAGE` of no numbers returns `#DIV/0!`.
  - Directly referenced empty cells are `0` in arithmetic and `""` in concatenation.
  - Text that cannot be converted to a number in arithmetic gives `#VALUE!`; `TRUE`/`FALSE` coerce to 1/0 in arithmetic.
  - Unknown function names give `#NAME?`.
  - Number-like text converts in arithmetic only if it is plain ASCII decimal (`"5"`, `" 1e2 "`); `"inf"`, `"1_0"`, `"0x10"` and non-ASCII digits give `#VALUE!`. A number outside the float range typed into a cell stays text; in a formula it is a syntax error. Arithmetic or `SUM`/`AVERAGE` overflow gives `#NUM!`. Negative zero never appears.
  - Limits (Excel's own): a formula is at most 8,192 characters and 64 levels of nested parentheses and function calls, with clear error messages when exceeded.
  - Syntax errors are rejected at entry: the edit is not applied and the user gets a message (the previous cell content is kept).

## 7. Dates and formats

- Dates are stored as a float serial number of days since 1 Jan 1900, **replicating Excel's 1900 leap-year bug**: serial 60 is the nonexistent 29 Feb 1900, so serial 1 = 1 Jan 1900 and serial 61 = 1 Mar 1900. Fractional part = time of day.
- Date recognition: on entry, text matching a supported date pattern (`DD/MM/YYYY`, `YYYY-MM-DD`) is converted to a serial number and the cell format is set to a matching date format.
- **Supported format codes (v1):** `General`; number formats using `0`, `#`, `,`, `.` with optional literal prefix/suffix (`$`, `%`); date tokens `DD`, `MM`, `YYYY`, `YY`, `MMM`, `HH`, `mm`, `SS`. The set is documented and extended through tests.
- Formats can be applied to a single cell or a range. Format changes do not trigger recalculation.
- Format strings are interned in a shared table (see section 5).

## 8. Dependency graph

- Directed acyclic graph with an **adjacency list in both directions**:
  - `dependencies[cell]`: cells this cell reads (used when recalculating: pull values from these).
  - `dependents[cell]`: cells that read this cell (used to find what to recalculate).
- An **in-degree map** is maintained for the affected subgraph during ordering.
- **Kahn's algorithm** performs the topological sort and detects cycles in one pass (nodes left unprocessed indicate a cycle).
- **Localised Kahn:** on a change, collect only the cells reachable downstream via `dependents` from the changed cell(s), then run Kahn on that subgraph only.
- **Range dependencies:** ranges are stored as range nodes, not one edge per cell, so that `A1:A1000000` costs O(1) edges. A change at `(r, c)` finds the range nodes covering it via an index (for example, per-column interval lists). Only populated cells are iterated when a range is evaluated.
- **Atomic edits with rollback:** setting a cell's formula builds the new dependency edges speculatively, runs the cycle check on the affected subgraph, and either commits or restores the previous edges, text, AST and values exactly. A rejected edit tells the user it would create a circular reference and leaves the sheet unchanged (there is no `#CIRC!` value: a cyclic edit is simply refused). Self-reference (`A1 = A1+1`) is covered explicitly.

## 9. Parallel recalculation

- After the graph is ordered, independent nodes are evaluated in parallel by a **thread pool** (`concurrent.futures.ThreadPoolExecutor`, sized to CPU cores) using task-based parallelism.
- Dispatch uses a **pending-dependency counter** per cell (initialised from the in-degree within the subgraph). When a cell finishes, it decrements its dependents' counters, under a lock-protected decrement (Python has no lock-free atomics; the lock must be tiny and per-cell or striped). A cell whose counter reaches zero is submitted to the pool. A global outstanding-task counter signals completion.
- Evaluation of a cell only reads the values of its dependencies (already final) and writes its own value, so no two tasks write the same cell.
- **Sequential fallback:** if the affected subgraph is smaller than a configurable threshold (default to be set from benchmarks), recalculate on the calling thread to avoid overhead.
- Large range functions may additionally be split into parallel partial reductions when benchmarks show a gain.
- **Benchmark suite** (`benchmarks/`): graph shapes (wide fan-out of independent chains, deep chain, diamond lattice, large `SUM` range) with per-cell work that is realistic and also artificially heavy. Reports speedup versus single-threaded at 1, 2, 4, N threads. Success criterion: on the wide independent-chains benchmark with sufficiently heavy cells, speedup at N cores is at least `0.5 * N` (target to be tuned after the first run); deep-chain benchmarks must show no significant slowdown from the pool.

## 10. Threading and edit model

- The engine is a **separate process** (section 14). It handles **one request at a time**, in order, from a single loop; each edit is one transaction (parse, update graph, cycle check, commit or roll back, recalculate). Edits sent while a recalculation runs simply wait their turn in the pipe, and the UI shows a "Calculating..." indicator if a request takes more than 150 ms.
- Only the Qt GUI thread touches Qt objects, in the UI process. The engine's worker threads never see Qt; they are used only for recalculation.
- **No read/write lock is used, by decision** (the original spec asked for one). Mutation of the graph and cell store happens only on the engine's single request thread, while recalculation workers run only when that thread is blocked waiting for them; workers read other cells (finished earlier in the plan, or unchanged) and write only their own cell. So nothing mutates the structures concurrently, and a lock would protect against nothing. This was checked empirically: 200 random graphs of 300-1,500 cells and 300 repeated runs gave identical results sequentially and with 6-8 threads. If the engine ever gets more than one caller thread, a lock must be added at that point.
- Readers never block the engine: the UI model asks for blocks of cells and shows the last data it has until a fresh block arrives.

## 11. Transactions, undo and redo

- Every user action (edit, format change, paste, fill, row/column insert/delete) is a single **transaction** recorded as a reversible set of cell changes (text, AST, value, format and graph edges).
- The same mechanism provides cycle rollback (section 8) and **undo/redo**: undo applies the inverse change set and recalculates the affected subgraph; redo reapplies it.
- Undo history is bounded two ways: 100 steps and 1,000,000 changed cells in total (oldest steps are dropped first). A single change larger than that is applied but cannot be undone, which clears the older history and tells the user. A new action after an undo clears the redo stack.

## 12. Structural edits, copy/paste and fill

- **Insert/delete rows and columns:** cell keys shift and every formula reference is adjusted (references to deleted cells become `#REF!`; ranges shrink or grow as in Excel). The graph is rebuilt for the affected cells as one transaction. Limits: operations that would push cells beyond the grid bounds are rejected.
- **Copy/paste:** formulas are copied with relative references adjusted by the paste offset (absolute `$` parts are not). Pasting a range is a single transaction. Values-only paste is supported.
- **Fill-down / fill-right:** same adjustment rules as copy/paste.
- Reference adjustment is performed on the parse tree, and the `text` is regenerated from it (re-parsed from the unfolded formula, because the stored AST has constants folded away; entry 67). Cut/move is not implemented.
- Fill, paste and paste-from-text write at most 250,000 cells in one operation; larger ones are refused with a message (an accidental select-all would otherwise freeze the engine). Formatting is capped at 1,000,000 cells.

## 13. CSV import/export

- Export writes display values or raw text (selectable); import reads each field through the normal entry path (so formulas and dates are parsed) as one transaction.
- Standard CSV quoting rules (RFC 4180) and UTF-8 encoding.
- Formats are not stored in CSV.

## 14. User interface (PyQt6)

- The UI runs in its own process (standard Python 3.14 + PyQt6) and starts the engine as a subprocess, talking to it with one JSON object per line over the engine's stdin/stdout (`sheet/server/protocol.py`). The engine never dies because of what arrives: every line gets a typed reply.
- `QTableView` with a `QAbstractTableModel` over the full 1,048,576 x 16,384 grid. `data()` never blocks: it answers from a cache of 64 x 16-cell blocks and requests missing blocks asynchronously.
- Name box, formula bar (Enter commits, Escape abandons), in-cell editing with Enter moving down, selection, copy/paste (formula-aware inside the app, tab-separated text outside), paste values, clear, fill down/right, undo/redo, nine format presets plus a custom format, row/column insert/delete, context menus, status bar (messages, engine mode, "Calculating...").
- Files: New, Open, Save, Save As for the native `.sheet` format (versioned JSON, atomic save), with a modified marker and a confirmation before unsaved changes are discarded; CSV import and export are separate.
- Display text comes from `value` plus `format`; errors display their code. Numbers are right-aligned, text left, booleans centred, errors red.
- Robustness: a global exception hook reports an unexpected error in the status bar instead of letting PyQt6 abort the process; the row and column headers do not track the selection (otherwise select-all froze the window for ~15 s).

## 15. Required test coverage (minimum)

- Lexer and parser: precedence, associativity, unary operators, strings, references, syntax-error cases; property tests that parsing then rendering then parsing is stable.
- Constant folding: `=1/2` yields a `Literal(0.5)` AST and text `"=1/2"`; verify no re-parse occurs during recalculation.
- Evaluator: coercions, empty cells, error propagation, all functions including ranges.
- Dates: serial conversion round trips, including 28 Feb, 29 Feb (bug), and 1 Mar 1900.
- Formats: each supported code with example values.
- Graph: add/remove edges, localized Kahn subgraph extraction, cycle detection (self, direct, indirect), rollback restores the exact prior state; property tests on random DAGs.
- Parallel recalculation: results identical to single-threaded results for random graphs; no cell evaluated before its dependencies; no cell evaluated twice per recalculation.
- Transactions: undo/redo round trips, including formats and structural edits.
- Structural edits and copy/paste: reference adjustment, `#REF!` generation, relative versus absolute.
- CSV: round trips, quoting, formulas and dates on import.
- UI (offscreen, against a real engine process): model size and `data()` output, edit round trip, queued edit during recalculation, every dialog path with scripted answers, the exception hook, and the application entry point.
- Robustness: fuzzing of the server loop and request handler; limits on formula size, nesting and operation size; numeric extremes (overflow, out-of-range numbers, negative zero); file permissions and symlinks on save.

## 16. Design decisions and issues found during implementation

A running log of decisions made and issues discovered while building. Newest entries go at the bottom.

### Tooling and platform
1. **PyQt6 has no wheel for free-threaded Python 3.14t.** `uv sync --extra ui` falls back to compiling PyQt6 from source, which hangs or fails. `scripts/setup.sh` installs the `ui` extra wheels-only (`--no-build`) and prints a warning when it is unavailable. The engine is unaffected, but the UI cannot run on 3.14t until a wheel exists. Options for step 7: run the UI on a standard 3.14 build with the engine on 3.14t, or wait for a wheel. Open decision.
2. **The `ui` dependencies are an optional extra**, not a core dependency, so that setup, tests and CI succeed for the engine without Qt.
3. **Layout:** the package is `sheet/` at the repo root and tests are in a top-level `tests/` directory (`tests/engine`, `tests/ui`), rather than nested under the package.

### Lexer and parser
4. **A reference-shaped word followed by `(` is a function name.** `LOG10(` matches the cell-reference pattern (`LOG10` is a valid column and row), so the lexer uses a negative lookahead and treats it as an identifier. Consequence: a function can never be named like a cell reference without parentheses ambiguity, and a reference directly followed by `(` is a syntax error.
5. **Reference bounds are checked in the parser, not the lexer.** `XFE1` and `A1048577` lex as references but are rejected with a syntax error.
6. **Unary minus binds tighter than `^`, as in Excel**: `=-2^2` is 4. `^` is right-associative (`=2^3^2` is 512), which differs from Excel (left-associative, giving 64). The spec and tests chose right-associative; this is a deliberate deviation from Excel and should be revisited if Excel fidelity matters. **[Superseded by entry 137: `^` is now left-associative, as in Excel.]**
7. **Ranges are normalised** so that `start` is the top-left and `end` the bottom-right (`B2:A1` becomes `A1:B2`), with `$` flags following their coordinate.
8. **Function names are upper-cased at parse time;** unknown names are only detected at evaluation (`#NAME?`), not at entry.
9. **Syntax errors are positional:** `FormulaSyntaxError` carries the character position, offset by 1 for the leading `=`.
10. **Numbers are always floats** in the AST (including integer literals) so there is a single numeric type through the engine.
11. **Whole-column and whole-row ranges (`A:A`, `1:1`) are specified (section 6) but not yet implemented in the lexer and parser.** To be added with the range dependency work. **[Resolved by entry 137: whole-column and whole-row ranges were removed from the spec.]**

### Evaluator and constant folding
12. **Folding evaluates against an empty reader** (`NO_CELLS`). Any sub-tree with only literals, including function calls such as `SUM(1,2)` and unknown functions, is replaced by a `Literal`. A constant error is folded into an error literal, so `=1/0` is `Literal(#DIV/0!)` and is never re-evaluated.
13. **Folding is purely structural.** Volatile functions (such as `NOW()` or `RAND()`) must not be folded if they are added later; the function registry will need a `volatile` flag.
14. **Comparison ordering** follows Excel: numbers < text < booleans; text compares case-insensitively; an empty cell compares as 0, `""` or FALSE depending on the other operand.
15. **Function argument rules are asymmetric.** A range or single-cell argument ignores empty, text and boolean cells (so `MAX(A1,10)` with text in `A1` ignores `A1`), whereas literal arguments are coerced strictly (`SUM("x")` is `#VALUE!`, `SUM(TRUE)` is 1).
16. **`MAX`/`MIN` of no numbers return 0** and `AVERAGE` of none returns `#DIV/0!`, matching Excel.
17. **Numbers convert to text with 15 significant digits** (`f"{x:.15g}"`), so `5.0` concatenates as `5`.
18. **Arithmetic results that overflow or are not finite give `#NUM!`**; `0^-1` gives `#DIV/0!`; a negative base with a fractional exponent (a complex result) gives `#NUM!`.
19. **`SUM` uses `math.fsum`** for accurate floating-point summation; results may differ in the last digit from a naive left-to-right sum, and from Excel.
20. **A bare range outside a function** (`=A1:A3`) evaluates to `#VALUE!`. Excel's dynamic-array spilling is out of scope.
21. **The evaluator reads cells through a `CellReader` protocol** (`get`, `range_values`) rather than a concrete store, so it can be tested with a fake and the real store plugs in later. `range_values` must return only populated cells, which is what makes huge ranges cheap.
22. **Recursion depth:** parsing and evaluation are recursive, so extremely deeply nested formulas could hit Python's recursion limit. A maximum nesting depth (with a syntax error beyond it) should be added. **[Resolved by entry 131: Excel's limits are enforced with clear messages and the recursion limit was raised.]**

### Dates and formats
23. **`make_serial` / `split_serial` return and accept floats**, and the fake `29 Feb 1900` (serial 60) is accepted on entry and displayed, but a real calendar has no such day, so `split_serial(60)` is special-cased. Dates before 1 Jan 1900 are rejected; serial 0 ("0 Jan 1900" in Excel) is not supported.
24. **Times are rounded to the nearest second** before display, and a value such as `45292.999999999` carries into the next day (`02/01/2024 00:00:00`) instead of showing `24:00:00` or `59` seconds.
25. **Date recognition on entry is limited to `D/M/YYYY` and `YYYY-M-D`.** `1/2/2024` is 1 February (day first), consistent with the `DD/MM/YYYY` default; US-style month-first entry is not supported. Ambiguity depends on locale, which is out of scope for v1.
26. **Format tokens are case-sensitive where needed:** `MM`/`MMM` are months and `mm` is minutes, because Excel disambiguates by context and we do not. `DD`, `YY`, `YYYY`, `HH` and `SS` also accept lower case. Single `D`, `M`, `H` etc. (no zero padding) and `MMMM`, `AM/PM` are not supported yet.
27. **A format is numeric or date, never both** (`0 DD` is a `FormatError`). Digit placeholders (`0 # , .`) must be contiguous, so Excel's `0 0` style patterns and multi-section formats (`pos;neg;zero`) are not supported.
28. **Numeric rounding is half away from zero**, done with `Decimal(repr(value))` rather than binary floats, so `2.675` formatted as `0.00` gives `2.68` as Excel does, not `2.67`.
29. **A value that rounds to zero shows no minus sign** (`-0.001` as `0.00` is `0.00`). Excel shows `-0.00`.
30. **Placeholder edge cases deviate from Excel:** `#` with 0 renders an empty string, and `#.##` with `1` renders `1` (Excel shows `1.` with a trailing point).
31. **`%` multiplies the value by 100** wherever it appears in the format. General format shows up to 10 significant digits (`0.3333333333`) and switches to exponent form for very large or small numbers.
32. **Non-numeric values ignore the format** (text, booleans, empty and errors display as General), but an invalid format string raises `FormatError` even then, so bad formats are caught when they are set.
33. **Format strings are compiled once and cached** (`lru_cache`), so rendering a visible grid does not re-parse formats. The cache is thread-safe under free-threaded Python, but the interning of format strings in the cell (section 5) is not yet implemented.

### Entry parsing and the cell store
34. **`Cell.error` is derived, not stored.** The spec listed a separate "has error and message" field, but an `ErrorValue` in `value` already carries the kind and message, so a second field could disagree with it. `Cell.error` is a property returning the `ErrorValue` or `None`.
35. **Entry classification order is: empty, formula (`=`), leading apostrophe, number, boolean, date, text.** A leading `'` forces text (`'123` has value `"123"` and keeps the raw text). Numbers must match a strict pattern, because Python's `float()` would otherwise accept `inf`, `nan`, `1_000` and `infinity` as numbers. Thousands separators (`1,000`) and percent entry (`50%`) are not recognised and are stored as text.
36. **Whitespace around an entry is ignored when classifying** (` 42 ` is the number 42) but the raw text is stored unchanged. A whitespace-only entry is empty.
37. **Constant formulas get their value at entry time.** `=1/2` yields value `0.5` immediately with no recalculation, and `=1/0` yields `#DIV/0!`. Formulas with references have `value=None` until the first recalculation, so a freshly entered formula reads as empty to other cells until then; the coordinator must recalculate it in the same transaction.
38. **A date entry sets the cell's format only if its current format is `General`**, so typing a date into a cell formatted `0.00` keeps `0.00`. Typing a non-date over a date-formatted cell also keeps the date format (as Excel does).
39. **The store replaces `Cell` objects rather than mutating them** (`dataclasses.replace` for format changes), so a reader on another thread sees either the old cell or the new one, never a mix. Format strings are interned (`sys.intern`) when a cell is built.
40. **`range_values` walks the smaller of the rectangle or the stored cells.** Small rectangles are walked by coordinate and huge ones (`A1:XFD1048576`) by scanning the stored cells, so the cost is bounded by the number of populated cells. It skips cells whose value is `None` (empty cells, formatted-only cells and not-yet-calculated formulas). The scan path is O(stored cells) per call, so many large-range formulas over a big sheet will want a per-column or per-row index later; this is the first hot spot to measure.
41. **Formatting a range materialises empty cells**, capped at 1,000,000 cells (`MAX_FORMAT_CELLS`); larger rectangles such as a whole column are rejected with `ValueError`. Formatting entire rows or columns needs a separate style layer (column/row default formats) and is deferred. Applying a format is all-or-nothing.
42. **The store has no locking of its own.** Single dict operations are safe under free-threaded Python, and iteration copies (`list(...)`) to avoid "dict changed size" errors, but multi-step updates are made consistent by the engine's read/write lock (section 10), which does not exist yet. The concurrent-writers test only covers distinct keys.
43. **Bounds are checked on every access** (`IndexError` outside the 1,048,576 x 16,384 grid), including reads.

### Dependency graph
44. **Cycle detection and ordering are one pass.** `DependencyGraph.plan(changed)` walks the downstream subgraph with an iterative search (no recursion, so a 20,000-cell chain is fine), builds the in-degree map, then runs Kahn's algorithm on that subgraph only. Any node left unprocessed means a cycle. The same pass produces the evaluation order, the in-degree map and the successor lists that the parallel recalculation (section 9) needs, so a cycle check and a recalculation plan cost one traversal.
45. **`CycleError.cells` is every unprocessed node, not just the cycle members.** Kahn's algorithm cannot separate cells on the loop from cells merely downstream of it. If the UI should highlight only the loop, a second pass (for example finding strongly connected components) is needed. Open decision.
46. **Edits are atomic by install-check-restore.** `set_dependencies` removes the cell's old edges, installs the new ones, runs `plan([cell])`, and on any exception (not just `CycleError`) uninstalls the new edges and reinstalls the old ones, so the graph is identical to before. A property test compares random edit sequences against a brute-force cycle check and verifies the graph mirrors the model after every step, including after rollbacks.
47. **Only the edited cell needs checking for a new cycle.** The graph is acyclic before the edit, so any new cycle must pass through the edited cell. Kahn run from that cell therefore finds every cycle an edit can create. Self-references (`A1 = A1+1`) and cycles through a range (`C1 = SUM(A1:A3)` with `A2 = C1`) are both covered by tests.
48. **Ranges are single nodes (`Rect`)**, so `A1:A1000000` is one edge set entry. The reverse lookup "which ranges cover this cell" uses a per-column bucket index for ranges up to 64 columns wide, plus a list of wider ranges that is scanned linearly. Within a bucket every range is still checked for row containment, so a column with thousands of ranges costs thousands of comparisons per changed cell. An interval tree per column is the next step if benchmarks show this matters.
49. **`dependents(cell)` allocates and sorts a new set on every call**, and `plan` calls it for every downstream node. That is acceptable now and gives deterministic plans, but it will show up in profiles on very wide fan-outs.
50. **Seeds are part of the plan.** `plan([A1])` includes `A1` itself first, because a changed formula cell must be re-evaluated; a caller that only changed a constant can skip the first element. When several seeds are given and one is downstream of another, the in-degree map counts that edge, so ordering stays correct.
51. **Removing a cell drops only its own reads.** Cells that read the removed cell keep their edges, so they are recalculated (seeing an empty value) when the cell is cleared or overwritten. Deleting a row or column (section 12) will need its own graph rebuild.
52. **The graph is not thread-safe.** All mutation and `plan` calls must hold the engine's write lock (or read lock for `plan`) once the coordinator exists; nothing in the graph enforces this yet.
53. **Dependencies on out-of-bounds or `#REF!` cells are not represented.** The graph stores whatever coordinates it is given; bounds are enforced by the parser and cell store.

### Transactions, undo/redo and the `Sheet` facade
54. **Cells are immutable once stored, so a transaction is a before/after pair of cells per changed position.** Rollback after a rejected edit, undo and redo are all the same operation (`_put_all`): put these cells back. There is no separate "inverse operation" logic to keep in sync.
55. **The dependency graph is derived from the cells' ASTs and is never saved in a transaction.** Putting a cell back re-derives its edges with `extract_references`, using the unchecked `DependencyGraph.restore_dependencies`, because a state that existed before is acyclic. The invariant "graph edges equal the references in each cell's AST" is checked by a randomised test after every operation.
56. **Undo restores values as well as formulas.** Downstream cells recalculated during an edit are recorded in the same transaction, so undo and redo put exact values back and do not recalculate. This makes undo cost proportional to the cells that changed, but it means history holds a copy of every recalculated cell: one edit to a cell that feeds 100,000 formulas stores 100,000 before/after pairs per history entry. Memory use of the 100-step history needs a measurement, and a cap by cell count may be needed.
57. **A batch is checked once.** `set_entries` applies every cell and its edges, then runs a single `plan` from all changed cells. Any new cycle must pass through a changed cell, so one Kahn pass finds it, and the entire batch is rolled back. This makes paste, fill and CSV import O(batch + downstream) rather than one plan per cell. Entries are parsed and bounds-checked before anything is written, so syntax errors and out-of-range positions never reach the rollback path.
58. **Rollback also covers unexpected failures.** Any exception during the write or recalculation phase (not just `CycleError`) restores the touched cells and edges; a test injects a failure partway through recalculation. For a failed or no-op edit there is no history entry.
59. **No-op edits are not recorded.** If, after recalculation, no cell differs from before (for example retyping the same number into a cell), nothing is pushed to the undo stack and the redo stack is kept. "Differs" compares text, AST, format and value, with value comparison type-aware so `TRUE` and `1.0` are different.
60. **A formula that evaluates to an empty cell displays as 0** (`=A1` with `A1` empty gives `0`), as in Excel. Inside larger expressions the empty value is still treated as 0 or `""` depending on the operator.
61. **Clearing a cell keeps a non-General format.** An empty entry removes the cell only if its format is General; otherwise it leaves an empty formatted cell, as Excel's Clear Contents does. Typing into a cell keeps its existing format unless the entry is a date and the format is General (section 5, entry 38).
62. **Every formula in the downstream plan is re-evaluated, including ones whose inputs did not change value.** Pruning ("stop when a recalculated value is unchanged") is a possible later optimisation, but it interacts with the parallel dispatch counters, so it is deferred until after the parallel recalculation exists.
63. **Format changes are transactions without recalculation.** `Sheet.set_format_range` skips the graph and recalculation, since a display format never changes a value. It shares the 1,000,000-cell limit with the cell store (entry 41).
64. **`Sheet` is single-threaded for now.** It holds no locks; the edit queue, read/write lock and worker threads (section 10) are added together with the parallel recalculation. `set_entry` and friends return the set of changed positions so the UI model can emit precise `dataChanged` signals.
65. **Undo depth is bounded by a `deque(maxlen)`** (default 100); the oldest entry is dropped silently. The redo stack is a plain list cleared by any new edit.

### Structural edits, copy/paste and fill
66. **Error literals are part of the formula language.** `#REF!`, `#DIV/0!`, `#NAME?`, `#VALUE!`, `#CIRC!` and `#NUM!` lex as an `ERROR` token and parse to `Literal(ErrorValue(...))`, so a reference that loses its target can be written into the formula text (`=#REF!+1`) and parsed again. An error literal propagates through operators and functions like any other error cell.
67. **Formula text is regenerated from the unfolded parse, not from the stored AST.** Section 12 of the spec said to regenerate text from the AST, but the stored AST has constants folded (`A1+(2*3)` is stored as `A1+6`), so rendering it would silently change what the user typed. Instead a rewritten formula is `parse(text)` (unfolded) -> rewrite references -> `render` -> `compile` again, so the stored AST stays folded. Whitespace and redundant parentheses in a *rewritten* formula are normalised (`=A2+(2*3)` becomes `=A3+2*3`); formulas whose references do not change keep their exact text. A cheap pre-check on the folded AST (folding never removes a reference) skips the parse for unaffected formulas.
68. **`render` uses minimal parentheses and round-trips.** `parse("=" + render(node)) == node` for every tree the parser can produce, verified by a property test over random trees. Precedence levels mirror the parser: `^` is right-associative and a prefix minus binds tighter than `^`, so `-(2^2)` keeps its parentheses and `-2^2` does not. Non-finite number literals (from `1e999`) cannot be rendered and raise `ValueError`.
69. **Insert/delete follow Excel's range rules.** Inserting inside a range or at its start expands or shifts it; inserting just after its last row leaves it alone. Deleting rows shrinks a range, and a range entirely inside the deleted band (or a single reference into it) becomes `#REF!`. Absolute (`$`) references are re-pointed too, since they name cells, not offsets. Only copy, paste and fill treat `$` as fixed.
70. **Structural edits are one transaction, built as a diff.** Every stored cell is mapped to its new position and rewritten; only cells that moved or whose formula changed are put in the change set, plus the positions they vacate. The change set goes through the same commit path as any edit (one recalculation, one cycle check, one undo step, full rollback on failure), and undo restores moved cells, rewritten formulas and values exactly.
71. **Inserting rows or columns that would push a populated cell off the grid is rejected** with `ValueError` and no change; deleting rows or columns past the used area is a no-op that records no history. Argument errors are `ValueError` (count below 1) or `IndexError` (index outside the grid).
72. **Only cells that moved or changed text are recalculated.** A formula whose references are unchanged is not re-evaluated even if it reads cells that moved, which is safe because moves are monotonic: a cell cannot cross a range boundary, and any reference or range that changes shows up as changed text. The randomised test checks values against a fresh rebuild after every operation.
73. **Cost of structural edits is O(populated cells).** Every stored cell is visited to compute its new position. A million-cell sheet therefore pays a full pass per insert or delete; an offset-based row/column index would avoid that but is not needed at the sizes planned for v1.
74. **Paste copies formulas (references shifted), values and formats; empty cells in the copied area clear their targets.** A relative reference shifted off the grid becomes `#REF!`. The clipboard is a snapshot, so copying and pasting over overlapping areas is safe. A paste whose rectangle would leave the grid is rejected. Cut/move is not implemented, since moving a formula without rewriting references to it needs its own semantics.
75. **Paste-values writes constants.** Numbers, booleans and text are written as ordinary entries (text that would otherwise parse as a number, date or formula gets a leading apostrophe), errors are written as `=#DIV/0!` style constant formulas, and target formats are kept. A `values_only` paste of an empty formatted cell clears the target but keeps its format.
76. **Fill copies the first row (down) or first column (right) of the selection** into the remaining cells as a single transaction. Series fill (1, 2, 3 continuing a pattern) and drag-fill extension are not implemented.
77. **`CellStore.cells_in` generalises the range scan.** `range_values`, copy and paste share one routine that walks the cheaper of the rectangle or the stored cells (entry 40), so copying `A1:XFD1048576` costs the number of populated cells.

### Parallel recalculation
78. **The scheduler is generic.** `ParallelRecalculator.run(plan, compute)` knows nothing about cells or formulas: it takes the plan from `DependencyGraph.plan` (in-degree map and successor lists) and calls `compute(node)` once per node, each after all its dependencies. `Sheet` supplies a `compute` that evaluates one cell and writes only that cell. Tests check, from several threads, that every node runs exactly once, never before a dependency, and that results equal the sequential run for random DAGs.
79. **Work is dispatched in batches with worker-side continuation.** Each node has a pending-dependency counter (striped locks, since Python has no lock-free atomics). A worker keeps the nodes it unlocks and runs them itself, so a chain costs no pool round trips. It hands work back to the pool when it holds more than `2 * grain` nodes, or when pool threads are idle and it holds several (half go back, so work spreads by repeated splitting). An `AtomicCounter` of outstanding tasks signals completion, and the calling thread also works. A final check that exactly `n` nodes ran guards against scheduler bugs.
80. **A chain cannot migrate between threads.** A worker holding a single unlocked successor never sheds it (a hand-off costs about as much as a cell), so a chain that starts on a slow core finishes on it. On a machine with performance and efficiency cores this limits scaling beyond the number of fast cores.
81. **Failure handling.** The first exception raised by `compute` stops new nodes starting, running tasks finish, and the exception is re-raised on the calling thread; `Sheet` then rolls the whole transaction back (entry 58). The pool stays usable afterwards.
82. **Small plans run sequentially.** Plans under `parallel_threshold` cells (default 256), a single worker, or a closed `Sheet` run on the calling thread, so an ordinary edit pays no pool cost and tests that create many sheets do not create thread pools. The default threshold is a guess; it should be tuned from benchmark data on target hardware.
83. **Finding: reading shared cells does not scale under free-threaded Python.** Scanning a range cell by cell touched shared `Cell` and float objects, and every thread updates the same reference counts: 1 to 8 threads scanning the same 2,000 cells went from 60 ms to 91 ms in total. The same reads from an `array('d')` scale about 3x. This is a property of the free-threaded runtime, not of the scheduler (a pure CPU workload through the same scheduler scaled about 3x), and it makes the "flush into compact arrays before running in parallel" idea in the original spec worth something after all.
84. **Range snapshots.** Before a recalculation, any range that at least 4 planned formulas read, and that contains no formula about to be recalculated, is packed once into a `RangeSnapshot` (an `array('d')` of its numbers plus its first error). The evaluator's `SUM`, `AVERAGE`, `MAX`, `MIN` and `COUNT` use the snapshot when the reader has one and fall back to the live scan otherwise; a property test checks both paths agree. Snapshots are built for sequential runs too (so the benchmark baseline is fair, and a sheet of 1,000 `=SUM($A$1:$A$2000)` formulas does one scan instead of 1,000) and are always released, even if recalculation fails. Ranges containing recalculated formulas are read live, which is correct but does not scale.
85. **Hot single cells still contend.** A cell read by many formulas (a tax rate, a seed) is a shared object whose reference count every thread updates; the `fan_out` benchmark, where all cells read one seed, scales worst. A per-thread copy of hot values is a possible fix but is not built.
86. **Benchmark results** on a 10-core Apple machine (4 performance, 6 efficiency cores), free-threaded 3.14.8, 4 workers vs sequential: `wide` (64 chains x 20 cells) 2.8x, `fan_out` (1,500 independent cells on one seed) 2.7x, `lattice` (32 x 20 diamond mesh) 2.9x, and `deep` (one 600-cell chain) 1.0x, i.e. no overhead. Speedup peaks at 4 workers and falls to 1.5-2x at 8-10 (entry 80). The pass criterion is therefore 0.5 x min(4, CPUs) x for the parallel shapes and at most 1.3x slower for the chain, which the machine meets with margin (target 2.0x).
87. **Benchmark layout.** `benchmarks/shapes.py` builds the shapes, `benchmarks/run.py` prints the table and, with `--check`, enforces the targets; `scripts/bench.sh` runs it plus the `benchmark`-marked pytest check. Timing tests are deselected from the normal test run (they are machine-dependent), and a fast smoke test checks that every shape gives identical results for 1, 3 and 6 workers. CI on shared runners should run only the smoke test.
88. **Locking is still outstanding.** `Sheet` itself remains single-threaded: the edit queue, the read/write lock (section 10), and the GUI-thread signal bridge are built with the UI. Workers are safe today because each writes only its own cell and reads only cells that finished earlier in the plan, and snapshots are only built and released on the calling thread.

### CSV import and export
89. **Import is an ordinary edit.** Every field goes through `Sheet.set_entries`, so numbers, booleans, dates (`25/12/2024` becomes a date with a date format) and formulas are parsed exactly as if typed, the import is one transaction (one recalculation, one undo step), and a circular reference rolls the whole import back. A quoted field starting with `=` is still a formula, as in Excel. Leading zeros are lost (`007` is the number 7); a leading apostrophe (`'007`) keeps text.
90. **Empty fields clear their target cells,** as paste does, so importing over existing data replaces the whole rectangle covered by the file, including blanks. Cells outside the file's rectangle are untouched. Ragged rows are allowed (short rows leave the remaining cells alone).
91. **All-or-nothing with located errors.** A malformed formula raises `CsvError` carrying the 0-based row and column and the cell name (`B2: ...`); `bad_formulas="text"` instead keeps it as text (with a leading apostrophe) and continues. A file too big for the grid at the chosen position, an over-long field (more than 131,072 characters, the `csv` module's limit), or a NUL byte also raise `CsvError`. In every case the sheet is unchanged.
92. **Export has two modes.** `display` writes each value as shown (formats applied: `$1,234.50`, `25/12/2024`, `TRUE`, `#DIV/0!`); `raw` writes the text as typed, formulas included, which is the mode that reproduces a sheet on import. A property test exports random sheets raw and re-imports them and checks text, value type and value of every cell. A display export of numbers can lose precision (formats round) and of formulas loses the formula.
93. **Export always starts at A1** so positions survive a round trip, pads gaps with empty fields, and can take a rectangle. A sheet with one cell far down or right writes every row up to it as mostly empty lines; a million-row used range is written in full.
94. **Encoding and dialect.** Export is UTF-8 (no byte-order mark) with `\r\n` line endings and minimal quoting (fields with delimiter, quote or newline are quoted, quotes doubled). Import reads `utf-8-sig`, so a leading BOM from Excel is accepted. The delimiter is a parameter (comma, semicolon or tab). Other encodings, locale number formats (`1,5` as 1.5) and header-row handling are not supported; formats and column widths are not stored in CSV.
95. **Source and destination can be a path or an open text stream** (files are opened with `newline=""` so embedded newlines survive).

### UI research: running a Qt UI next to a free-threaded engine (findings)
99. **No Qt binding for Python has a free-threaded wheel.** Checked against the package index: PyQt6 6.11.0 and PySide6 6.12.0 publish only `cp310-abi3` wheels, which cannot install on a free-threaded build, and no release of either has ever had a `cp313t` or `cp314t` wheel. Riverbank's mailing list shows the free-threading question (April 2025) without a reply; Qt's own notes say PySide6 support is a research effort with Quansight, needs a custom locking scheme around the Qt event loop, and may land in PySide7 rather than PySide6. (A compatibility tracker page claiming PySide6 6.12.0 support contradicts both the package index and Qt's 6.12 release post, and appears to be wrong.) Sources: [Qt for Python development notes](https://wiki.qt.io/Qt_for_Python_Development_Notes), [Qt for Python 6.12 release post](https://www.qt.io/blog/qt-for-python-release-6.12-is-here), [PyQt mailing list, April 2025](https://riverbankcomputing.com/pipermail/pyqt/2025-April/046182.html).
100. **PyQt6 on a standard 3.14 build works and meets the spec's UI requirement.** Tested here: PyQt6 6.11.0 (Qt 6.11) installs from a wheel on Homebrew's Python 3.14.8, and a `QTableView` over a `QAbstractTableModel` reporting 1,048,576 x 16,384 shows and scrolls to row 900,000 without trouble. Pitfall: `uv venv --python 3.14` here selected the free-threaded build when one was installed; the standard build must be requested explicitly (for example by path).
101. **Out-of-process engine is fast enough.** Prototype: the engine runs on 3.14t (GIL off) in a subprocess and a client on standard 3.14 talks to it with JSON lines over pipes. Fetching a 40 x 20 viewport (800 cells, formatted) took 0.37 ms median; 60 x 30 (1,800 cells) 0.8 ms; an edit plus a viewport refetch about 0.2 ms; all far under a 16 ms frame. This keeps the engine parallel and the UI on PyQt6, at the cost of a process boundary: the UI model needs a viewport cache, asynchronous fetching, and change notifications pushed from the engine.
102. **Tkinter works on 3.14t out of the box** (Tk 9.0, `Tk()` created and destroyed, GIL stayed disabled), so a single-process UI is possible without Qt. It has no virtualised table: `tksheet` (pure Python) keeps data in memory and its README says development has ceased apart from bug fixes, so a 1M x 16k grid would need a custom canvas widget (draw only visible cells, manage scroll offsets manually).
103. **Library availability on free-threaded Python** (package index, latest releases): free-threaded wheels exist for pyobjc (macOS bridge used by pywebview), websockets, aiohttp, pydantic-core, msgpack and pyzmq; none have ever been published for wxPython, Kivy, Dear PyGui, pygame, imgui-bundle or orjson (so NiceGUI, which needs orjson, would have to build it from source). Pure-Python wheels (install anywhere): textual, tksheet, pywebview, pyglet, flet, nicegui, starlette, uvicorn. pywebview needs pyobjc on macOS, pythonnet plus WebView2 on Windows, and Qt or GTK (PyGObject) on Linux, so free-threaded support there is unverified.
104. **Candidate approaches, in order of fit** (decision pending):
    - **A. PyQt6 UI on standard 3.14 plus the engine as a 3.14t subprocess.** Meets the spec exactly and keeps parallel recalculation. Costs an IPC layer (engine server, UI-side client and cache). The engine API is already UI-agnostic, so the same server would serve other front ends.
    - **B. Tkinter with a custom canvas grid, single process on 3.14t.** One interpreter, no IPC, parallel recalculation preserved; but departs from the spec's PyQt6/`QTableView` choice and means writing the grid widget (selection, editing, scrolling, headers) by hand.
    - **C. Web front end (browser or pywebview) talking to a websocket server in the engine process.** Free-threaded wheels exist for the server libraries; a canvas-based JS grid does virtualisation. Largest amount of new code (JS plus protocol) and a second language.
    - **D. PyQt6 in-process on standard 3.14, accepting the GIL.** Simplest, but recalculation loses its parallel speedup (the benchmark shapes would show about 1.0x), which defeats a main goal of the spec.
    - **E. Terminal UI (Textual, pure Python).** Runs on 3.14t today but is not the spec's UI and is awkward for a 1M x 16k grid.

### The UI: engine process, protocol and PyQt6 front end (option A)
105. **Decision: option A.** The UI runs on standard Python 3.14 with PyQt6 (a `QTableView` over a `QAbstractTableModel`, as the spec requires) and starts the engine as a subprocess on free-threaded 3.14t. This keeps parallel recalculation and the spec's UI toolkit. Cost: two interpreters, two virtual environments (`.venv` for the engine, `.venv-ui` for the UI, both created from the one `pyproject.toml` by `scripts/setup.sh`; the UI environment is selected with `UV_PROJECT_ENVIRONMENT`, and its interpreter is chosen by `scripts/ui_python.sh`, which picks an installed CPython 3.14 whose reported variant is `default` and installs one if none exists; see entry 116), and a process boundary.
106. **The protocol is one JSON object per line.** `sheet/server/protocol.py` has a `Session` (one open sheet plus the copy clipboard) whose `handle(request)` never raises: every failure becomes `{"ok": false, "error": {"kind", "message"}}` with a kind the UI can act on (`syntax`, `circular`, `format`, `csv`, `io`, `invalid`, `internal`). Every success carries the document `version` and `can_undo`/`can_redo`. Requests are matched to responses by `id`. `sheet/server/main.py` serves it on stdin/stdout, redirects stray prints to stderr so stdout carries only protocol messages, exits when stdin closes, and survives malformed lines. The protocol is toolkit-independent, so a different front end could reuse it.
107. **A view response carries just what is shown.** `view` returns, for a rectangle (at most 20,000 cells), `null` for empty cells or `[display, kind]` where kind is `n`/`s`/`b`/`e` (number, text, boolean, error); the raw text is added as a third element only when it differs from the display text (formulas, formatted numbers), so the model can edit and fill the formula bar without a blocking request. Changes report either the list of changed cells or, above 5,000, only their bounding rectangle; the UI invalidates by bounds, which is safe because every moved or changed cell lies inside it.
108. **The model never blocks on the engine.** `SheetModel.data()` answers from a cache of 64 x 16-cell blocks (blank if a block has not arrived) and requests missing blocks asynchronously; the view repaints when a block lands. Old blocks are evicted beyond 600. An edit, structural change or undo refetches the cached blocks overlapping its bounds, showing the old text until the new arrives (no flicker); a block that was invalidated while its fetch was in flight is refetched on arrival. Because the engine answers requests in order, a fetch sent after an edit always sees the edit.
109. **The client is event-driven, not threaded.** `EngineClient` wraps `QProcess`: writes are queued, `readyReadStandardOutput` parses lines, callbacks run on the GUI thread, and an unexpected exit fails all pending requests with an `engine` error and emits `failed` (the window then disables itself and says so). Measured round trips from a standard-Python client to the engine (entry 101): about 0.4 ms for a 40 x 20 view and about 0.2 ms for an edit plus refresh, far under a frame, so there is no need for a faster transport.
110. **Pitfall found while building: do not name a model method `submit`.** `QAbstractItemModel.submit()` is a Qt virtual that Qt itself calls whenever the current cell changes; overriding it with a different signature aborted the process inside Qt. The model's method for sending a change is `send`.
111. **Window.** Name box (type `B7` to jump; invalid names are rejected and reverted), formula bar (Enter commits, Escape abandons, and it is not overwritten by incoming data while being edited), in-cell editing through the standard delegate with Enter moving down, File (open CSV at the cursor, save CSV as displayed values or as formulas), Edit (undo, redo, copy, paste, paste values, clear, fill down/right, insert/delete rows and columns using the selected rows or columns as the count), Format (nine presets plus a custom format), and a right-click menu on cells and headers. Numbers are right-aligned, text left, booleans centred, errors red. The status bar shows messages (red for errors, cleared after 8 s), the engine's mode (free-threaded, GIL off) and a "Calculating..." indicator that appears only if a request takes more than 150 ms, so quick edits never flash it.
112. **Clipboard.** Copy asks the engine to snapshot the selection (so pasting inside the app shifts formula references and carries formats) and puts the displayed values on the system clipboard as tab-separated text. Paste uses the engine's snapshot if the clipboard text is still what was copied, otherwise enters the clipboard text as tab-separated cells (formulas and dates parsed as if typed). Copy text is clamped to the used range, so selecting a whole column (a million rows) costs nothing. Cut and move are not implemented (entry 74).
113. **Selection-based commands.** `Delete` clears only populated cells (a `clear` request, so select-all then Delete is instant and one undo step per selected range) and keeps formats. Formatting a range larger than 1,000,000 cells, such as a whole column, is rejected with a message (entry 41). Fill needs a selection of more than one row or column and says so otherwise.
114. **Testing the UI.** UI tests (78) run in the standard-Python environment against a real engine subprocess (no mocks): protocol client, model caching and invalidation, and window behaviour driven with the Qt test tools on the offscreen platform. In the engine environment, where PyQt6 is absent, they are skipped. A helper waits by running the event loop, because `pytest-qt` would fail to load in the engine environment. The window was also run headlessly and screenshotted to check the rendering. A test bug worth recording: counting calls from several threads with `len(list)` can miss an exact value (two threads both see 21); use `AtomicCounter` (this made one recalculation test fail about once in 150 runs).
115. **Not built / known gaps.** (Native save/load was added later, entries 118-125.) No column width persistence, no cut/move, no keyboard shortcut for jumping to the used range, no drag-fill handle, no multi-range copy (the last selected range is used), and no row/column header selection-count feedback. The engine launcher assumes `.venv` next to the code (or `SHEET_ENGINE_PYTHON`, or falls back to `uv run`). The CI Qt libraries list (`libegl1`, `libgl1`, `libxkbcommon0`, `libdbus-1-3`, `libfontconfig1`, `libglib2.0-0t64`) was a guess for Ubuntu 24.04 and turned out to be sufficient (entry 117).

116. **First CI run: the UI environment could not be created.** The workflow's first run failed in `setup.sh` with `No interpreter found for Python 3.14+gil in managed installations or search path`. The `3.14+gil` request had worked locally only because Homebrew's 3.14 happened to be installed; on a clean runner uv found nothing and did not download it. Fix: `scripts/ui_python.sh` lists installed interpreters (`uv python list --only-installed --output-format json`), picks a CPython 3.14 with `variant == "default"`, runs `uv python install 3.14` if there is none, and prints the path; `setup.sh` creates `.venv-ui` from that path, and every other script and the workflow use `.venv-ui/bin/python`. Verified locally by deleting `.venv-ui`, and by simulating a clean machine (empty uv install directory, PATH without Homebrew), which downloaded a standard 3.14.8 and returned its path. The "Summarise test results" step also failed in that run, only as a knock-on (no report files); the summary script now ignores missing files.
117. **CI verified on GitHub.** After the fix in entry 116 the whole workflow passes on `ubuntu-latest` in about 47 seconds: both environments install from scratch, lint and type checks pass in both, all 453 engine tests pass on free-threaded 3.14t on Linux, all 78 UI tests pass (standard 3.14 + PyQt6 on Qt's offscreen platform, driving a real engine subprocess), the report summary is written, and the test-count badge is published to the `badges` branch. The README shows both badges ("tests passing" and "531 passed"). Confirmed by screenshots of the run and of the rendered README; the first run on a clean machine caught a bug that local runs could not (entry 116), which is the reason to keep CI even for a single-developer project. The timing benchmarks still run only locally (entry 96).

### Native save and load
118. **Format: versioned JSON, one cell per line.** `{"format":"sheet","version":1,"formats":[...],"cells":[` then one `[row, col, text]` or `[row, col, text, format_index]` per line, sorted by position, then `]}`. It is valid JSON, human-readable, deterministic (the same sheet always produces the same bytes, whatever order it was typed in) and diffs well in version control. Formats are stored once in a table (`General` always first) and cells refer to them by index; `General` cells omit the index. Text is written as UTF-8, not `\u`-escaped.
119. **Values are not stored.** Only the text typed and the format are saved; values are recalculated on load (in parallel for large sheets, in one transaction). A file therefore cannot disagree with its own formulas, and the format stays small. Cost: loading a large formula-heavy sheet is a full recalculation rather than a read; a 10,000-formula sheet loads in well under a second.
120. **Saving is atomic.** The file is written to a temporary file in the same folder, flushed and `fsync`ed, then renamed over the target with `os.replace`; on any failure the temporary file is removed and an existing file is untouched (tested by making the rename fail). Saving to a missing folder or a read-only location is an `io` error.
121. **Loading builds a new sheet and swaps it in only on success.** `load_sheet` validates everything first (structure, version, formats, bounds, duplicates, formula syntax) and builds a fresh `Sheet`; the engine session replaces its document only if that returns. A bad file therefore leaves the open document, its undo history and the UI cache exactly as they were. Errors are specific: not a sheet file, bad or newer version (a file from a future version says so and is refused rather than misread), malformed cell N, outside the grid, unknown or unsupported format, a cell listed twice, a formula syntax error naming the cell (`B1: ...`), and a circular reference. Unknown extra keys are ignored, so a later version can add information that this one skips.
122. **A loaded document has no undo history,** and the saved format is applied as is: a date cell the user had set back to `General` stays `General` and is not re-detected as a date (typing would re-detect it, loading must not).
123. **Bug found by the round-trip property test:** formatting an empty cell as `General` stored a useless empty cell with text `""` and format `General`, which is the same as no cell. It is harmless on screen but made a saved-and-reloaded sheet differ from the original. `CellStore.formatted_cells` now returns "remove" for an empty cell left with the General format.
124. **Protocol and UI.** New requests `save`, `load` and `new`; `load` and `new` return `reset: true`, which makes the table model drop its entire block cache (old cells that no longer exist cannot be found by bounds). File errors use the kind `file`. The window has File > New, Open, Save, Save As (Ctrl+N/O/S/Shift+S), a title with the file name and a `*` when the engine's version differs from the version at the last save or load, a confirmation before New, Open or closing discards changes (Save, Discard or Cancel; Save runs a local event loop until the engine answers), and `.sheet` added to a name typed without an extension. CSV moved to Import and Export entries and is not a document: exporting does not change the file name or clear the `*`.
125. **Limits.** "Modified" compares engine versions, so editing and then undoing back to the saved content still shows `*` (a content hash would fix that). Column widths and the cursor position are not saved. There is no autosave, recent-files list or file locking, and two programs saving the same file at once is not detected. The shared name helpers (`column_name`, `cell_name`) now exist in three places (`engine/address.py`, `engine/csv_io.py`, `ui/names.py`) and should be merged.

### Hardening review (bugs found by probing and fixed)
126. **Method.** A review of the whole project: every stated limit in this log, about 30 adversarial probes run against the real code in isolated subprocesses (numeric extremes, deep nesting, hostile protocol input, huge operations, file handling), a stress comparison of sequential and parallel recalculation on large random graphs, test coverage (96% engine, 89% UI), and a dead-code scan. Probes and fixes are listed below; each fix has a regression test.
127. **The server could be killed by its input.** The first malformed line crashed it with an `UnboundLocalError` (a latent bug the tests missed because a valid request had always come first and left a stale variable), and invalid UTF-8, deeply nested JSON and a 6,000-digit integer all killed it too. Now every non-blank line gets exactly one reply, `NaN`/`Infinity` are refused as non-standard JSON, a request `id` may only be an integer or a short string (an arbitrary `id` was echoed back and could produce invalid JSON), a closed stdout ends the loop quietly, and `sys.stdout` is restored. Fuzz tests feed random bytes to the loop and random garbage and random valid command sequences to the handler.
128. **Numbers outside the float range and overflow.** Typing `1e999` stored infinity, after which any numeric format made every view of that block fail with an internal error, `SUM` of an infinity and its negative failed, and inserting a row failed for any formula containing `1e999`. Now such a number typed into a cell stays text, in a formula it is a syntax error, and `SUM`/`AVERAGE` overflow (`=SUM(1e308,1e308)`) gives `#NUM!` instead of an exception (which had also rejected unrelated edits whose recalculation overflowed). Number-like text converts only if it is plain ASCII decimal, so `"inf"`, `"nan"`, `"1_0"`, `"0x10"` and non-ASCII digits are `#VALUE!` in arithmetic and text on entry (the lexer is ASCII-only too). `format_value` returns `#NUM!` for a non-finite value as a last line of defence.
129. **Saved files lost their permissions.** The temporary file came from `mkstemp` (mode 0600), so every save forced 0600 even over a 0664 file, and saving through a symlink replaced the link. Now the temporary file is created with 0666 so the umask decides a new file's mode, an existing file's mode is kept, and a symlink is resolved so the real file is replaced.
130. **Undo history had no memory bound.** 100 edits that each recalculated 30,000 formulas grew the process from 86 MB to 761 MB. The history is now also capped at 1,000,000 changed cells (329 MB for the same scenario); see section 11.
131. **Formula limits.** Formulas reached only 983 terms in a sum, 81 nested parentheses and 74 nested functions, then failed with a raw `RecursionError` reported as an internal error. Now the limits are Excel's (8,192 characters, 64 levels, enforced in the parser with clear messages), the recursion limit is raised to 30,000 once (checked safe: 4,000-term formulas work on small-stack worker threads, and extreme depth still produces a Python `RecursionError` rather than a crash), left-associative chains reach 4,094 terms, and any recursion error that still escapes is reported as a formula problem. Length is checked on what the user types, not on text the program regenerates when it rewrites references (which can lengthen a formula). A deeply nested JSON file is a file error. A 20,000-argument `SUM` is now refused (it exceeds 8,192 characters).
132. **Operations that could freeze the engine.** Select-all then fill-down wrote 1,048,576 formulas in 24 s. Fill, paste and paste-from-text are now limited to 250,000 written cells (about six seconds worst case), refused instantly with a clear message and no change; a huge pasted string is rejected before it is split. Explicit file operations (CSV import, loading a file) are not capped; their cost scales with the file. Inserting or deleting rows took about 5 s on a 400,000-cell sheet (it rewrites every cell) and has no cap or cancel; see entry 142 for the speed-up (now about 2 s).
133. **The UI froze for 15 s on Ctrl+A.** Found by a failing test: Qt's row and column headers, which share the grid's selection model, asked it about every row and column of a selection to highlight it, 1,048,576 x 16,384 for select-all (14.6 s; 1.4 s for one column). Overriding `visualRegionForSelection` did not help (measured), but giving each header a private selection model made select-all instant (0.01 s) while header clicks still select whole rows and columns. Selected headers are no longer shown in bold.
134. **Qt aborts the process on any unhandled slot exception, and my own tests were crashing Python.** Measured: an exception escaping a slot ends the process with `SIGABRT` (exit 134) unless `sys.excepthook` is replaced. The application now installs a hook that logs the traceback and shows "Unexpected error" in the status bar. The test proving the abort ran a deliberately crashing subprocess on every UI test run, and macOS logged each as a crash report with a "Python quit unexpectedly" popup (14 reports in a day); that half of the test was removed. Lesson: never crash a subprocess on purpose in a test that runs routinely.
135. **Display fixes.** `General` shows integers up to 11 digits in full as Excel does (12345678901 had shown as `1.23456789e+10`; larger ones stay scientific), negative zero never appears (`=-A1` with `A1` empty showed `-0`; zero results are normalised where they are produced, at entry and in the display), and numbers of 1e21 or more under a numeric format show in scientific notation instead of 300-digit strings.
136. **Dialogs and entry point are now tested.** Every modal prompt is a small overridable method (unsaved-changes question, file choosers, text prompt, warnings), so tests script the answers: Save/Discard/Cancel on New, Open and close, save with and without a path, a failed save, the engine dying mid-save (a 60 s ceiling guards the local event loop), every file dialog, custom formats, and the entry point (`create_window`, a real application run that leaves no engine process behind).
137. **Decisions taken in this review.** (a) Whole-column/row ranges (`A:A`) are removed from the spec rather than built. (b) No read/write lock: the single-threaded request loop makes it unnecessary (section 10). (c) `^` is now left-associative like Excel (`=2^3^2` is 64), superseding entry 6 and a deliberate early choice; the renderer's parenthesising and the round-trip property test were updated with it. (d) macOS and Linux are the supported platforms; Windows is untested.
138. **Verified solid.** Parallel recalculation matched sequential exactly in 200 large random graphs (300-1,500 cells with ranges) and 300 repeated runs on 8 threads; comparisons involving empty cells behave as in Excel; the engine returned typed errors for 16 malformed argument shapes; a 30,000-cell dependency chain, a 50 MB text cell and a 20 MB request line all work; `uv.lock` is committed.
139. **Still open.** Structural edits on very large sheets are uncancellable (entry 132; their speed was improved in entry 142); the engine has no per-request time limit or cancel, so a pathological formula set could keep the UI in "Calculating..." indefinitely; the engine tests that assert wall-clock limits and the UI test waits could flake on a very slow machine (addressed in entry 140).
140. **Cleanup.** Removed code that production never used: `Shape` (benchmarks), `CellStore.set_format` and `set_format_range` (formatting goes through `formatted_cells` and `Sheet`), `is_date_format`, the graph-level `set_dependencies` and `range_count` (the real check-and-restore lives in `Sheet`; the graph tests keep an equivalent helper so `restore_dependencies` and `plan` are still tested together), the `ErrorKind.CIRC` value that nothing produced (a cyclic edit is refused, not stored as an error), and the `Session._display` wrapper. The three copies of the column-name helper are now one (`sheet/engine/address.py`), and the UI's name-box parser accepts ASCII digits only, like the formula lexer.
141. **Test hardening.** Coverage went from 96% to 98% for the engine (the server loop is now tested in-process, so it is no longer invisible to coverage) with tests for the edge cases it exposed: comparisons with empty cells, unary plus, `COUNT` of literals, format-validation messages, impossible times of day, a pool that refuses work, a plan that never unlocks a node, a handler bug, and a reply that is not valid JSON. Wall-clock assertions in tests now have roughly 10x headroom over measured times while still catching the real regressions (which took 15-24 s), the UI wait ceiling is 20 s, and the `fan_out` benchmark target is 0.4 x workers (it is limited by contention on one shared cell, entry 85) so it no longer passes by a hair.
142. **Faster structural edits (insert/delete rows and columns).** Profiling a 400,000-cell sheet (200,000 constants and 200,000 formulas) showed 60% of the time in rewriting formulas (each parsed twice), 30% recalculating values that could not have changed, and 10% bookkeeping. Four changes, each measured (insert rows, 400,000 cells): **5.3 s -> 4.3 s** (each rewritten formula parsed once, building the new cell from the tree it already has), **-> 3.4 s** (recalculate only formulas whose value may change: a shift of references never changes a value, so inserts recalculate nothing; a delete recalculates only formulas that lost a reference (`#REF!`) or had a range cut, plus what depends on them; `Effects` in `refs.py` reports this, and moved formulas carry their old value), **-> 2.1 s** (the per-cell rewrite runs on the thread pool for sheets over 20,000 cells, in chunks of 5,000, via the new ordered `ParallelRecalculator.map`; the graph and store are still updated serially in one transaction). Insert columns went 6.5 -> 2.5 s, delete columns 6.2 -> 2.6 s, delete rows 5.3 -> 2.0 s. A bug caught by an existing test on the way: a formula that folds to a constant error (`=A2+1` becoming `#REF!`) must still seed the recalculation, or formulas that read it keep stale values; carrying the old value is only for structural moves, never for paste (pasted references point at different cells).
143. **The range lookup was the real scaling problem, and is fixed.** Finding the formulas that read a changed cell scanned every range in the cell's column, so a bulk edit cost cells x ranges: rewriting 20,000 inputs with 8,000 running-total formulas (`=SUM(A1:A9)` down a column) took 5.7 s, and a 450,000-cell sheet with 50,000 such formulas did not finish an insert in over five minutes (this was the weakness predicted in entries 48 and 49). Each column's narrow ranges are now held in `_RowIntervals`: grouped by height class (`2**k`) and sorted by first row, so a lookup is a binary search per occupied class plus a look at the few ranges starting in a small window above the cell. The same 20,000-input edit takes 0.14 s with 8,000 ranges (and no longer grows with the number of ranges), and the 450,000-cell sheet inserts a row in 4.6 s. The index is checked against a brute-force scan by a property test through random adds and removes, and a regression test fails if lookups go back to scanning every range. Wide ranges (more than 64 columns) are still scanned linearly. Removing a range from a very long sorted list shifts the list, so undo or redo of a 50,000-range edit costs about 2 s.

144. **Second round of structural-edit speed-ups (measured against the previous commit, 800,000 cells, three alternating runs each).** Insert rows 5.82 s → 4.16 s, undo 1.32 → 0.75, redo 1.31 → 0.77, insert columns 6.07 → 4.81, delete columns 5.64 → 5.32, delete rows 4.73 → 4.33. Changes: (a) the default worker count is the CPU count capped at 4 (`SHEET_WORKERS` overrides), because on this 4-fast/6-slow-core machine more threads were slower for both recalculation and structural edits; (b) `_commit` reads old cells in one pass and builds the undo and redo maps in one loop, skipping the comparison for cells that are identical objects; (c) the pool workers compute each moved formula's references so the serial commit does not re-walk every AST; (d) rewrite chunks are 1,000 cells instead of 5,000. Tried and rejected, no gain: disabling or freezing the garbage collector, removing format-string interning.
145. **Cheaper commit for structural edits.** Timing inside `_commit` (800,000 cells) showed the commit is about 36% of an insert or row delete, split into reading old cells 0.22 s, store writes 0.24, graph update 0.46, diff before/after 0.45, history 0.09. Two changes: (a) cells a structural edit moves or vacates are passed as `certain` and recorded as changed without comparing old and new (only cells recalculation changes are compared), so a moved cell landing on identical content is now reported as changed, which is harmless for undo; (b) the pool workers return dicts and the merge uses `dict.update` and a set difference, cutting the merge from 0.56 s to 0.33 s. Row delete 4.15 s → 3.70 s in the phase timer. The delete profile also showed deletes are not slow in themselves: `delete_rows` costs the same as an insert, and `delete_cols(0)` is the worst case because it turns every formula into `#REF!` and recalculates them.
146. **Table-driven lexer and parser.** The lexer is one regex with a named group per token kind (alternatives in priority order: number before reference before name, `<>` before `<`), and `Token` is a `NamedTuple`. The five one-line binary-operator methods are replaced by precedence climbing over a single table (`_BINARY`); all binary operators stay left-associative, unary binds tighter than `^`, as before. Verified against a saved copy of the old implementation on 600,009 random and adversarial inputs (tokens, ASTs, error types and messages all identical). One real difference was found and fixed: a backtracking string pattern reported an unterminated string at the wrong quote, so the pattern is possessive (`*+`). One deliberate fix: lexer errors raised from `parse()` now report positions in the full text including the `=` (they were one character early). Parsing is about 20-25% faster (12.7 → 10.3 µs for `=SUM(A1:A9)+(2*3)`), less than hoped because building tokens and frozen-dataclass nodes dominates; tuple-based nodes were rejected because they would compare equal to unrelated tuples.
